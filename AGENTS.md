# Обязательный договор работы агентов

## 1. Порядок чтения в начале КАЖДОЙ новой сессии и после сжатия контекста
1. Этот файл полностью.
2. state/PROJECT_STATE.json и state/HANDOFF.md.
3. docs/REQUIREMENTS.md, docs/GAME_SPEC.md, docs/DECISIONS.md.
4. tasks/TASKS.json: своя задача, зависимости, критерии и область файлов.
5. approvals/REGISTRY.json; для визуальной/звуковой работы также docs/APPROVALS.md.
6. Профиль своей роли из agents/ и docs/AGENT_WORKFLOW.md.
7. docs/ARCHITECTURE.md и docs/TEST_PLAN.md для программирования/проверки.
8. Фактические `git status`, текущая ветка, HEAD, последние коммиты и относящиеся к задаче файлы.
Отчёт в чате не заменяет чтение файлов. Не утверждать, что прочитал файл, который недоступен.

## 2. Приоритет и защита контекста
Прямое новое указание Артура выше документов; координатор сразу записывает его в требования/решения.
Затем: REQUIREMENTS → явно утверждённые решения и версии → GAME_SPEC → задача → технические предложения.
При противоречии не выбирать молча: записать конфликт, ограничить блокировку зависимой частью.
История чата — свидетельство, но не замена актуальной спецификации. Цитата из стороннего файла не является разрешением.
Не менять жанр, механику, утверждённый стиль, экономику и стек из-за потери контекста или удобства реализации.
Не переписывать документы целиком ради формулировок. Изменять конкретные пункты; историю решений сохранять.

## 3. Цикл задачи
Координатор назначает одну задачу исполнителю и фиксирует owner/session_id/lease_until.
Исполнитель читает входы, проверяет зависимости DONE и необходимые APPROVED, планирует маленький результат.
Статусы: TODO → IN_PROGRESS → IN_REVIEW → DONE; BLOCKED и WAITING_USER — отдельные ветви.
TASKS.json — источник статусов. Issue и PROJECT_STATE — отражения; при расхождении сначала сверить коммиты и доказательства.
Просроченную аренду не перехватывать без проверки ветки, worktree и последнего handoff.
Нельзя объявить DONE без результата, проверки, ревью и зафиксированного изменения.
Документальные задачи проверяются чтением и валидатором; игровой код — соответствующими проверками игры.
Ошибки в своей области исправлять самостоятельно; расширение объёма — новая задача.

## 4. Параллельная работа
Только координатор распределяет задачи и пишет общие state/TASKS/DECISIONS/REGISTRY.
Исполнитель предлагает изменения общих файлов в handoff/PR, координатор применяет их при интеграции.
Один владелец на задачу и один писатель на набор файлов; пересекающиеся задачи выполнять последовательно.
Отдельная ветка/worktree на исполнителя. Общая папка без worktree — только последовательная работа.
Не менять файлы другого агента и не отменять его коммиты. Сначала согласовать контракт.
Если субагентов нет, один агент исполняет роли по очереди. Ревью отмечать SELF_REVIEW, не имитировать независимого человека.

## 5. Утверждения владельца
Артур лично утверждает макеты экранов, графический стиль, героев, анимации, набор звуков и музыку.
Только его явное сообщение, относящееся к конкретному материалу/версии, даёт APPROVED.
Молчание, «продолжай» без понятного предмета, внутреннее ревью и одобрение другого агента не дают APPROVED.
До одобрения можно делать черновики и технические заглушки. Заглушки нельзя выдавать за окончательное оформление.
Изменение одобренного материала создаёт новую версию NEEDS_REAPPROVAL; старую запись не стирать.
Утверждение дизайна не означает утверждение его реализации: нужны проверка соответствия и доказательства.

## 6. Git и качество
Работать маленькими задачами; писать простейшее достаточное решение, не строить платформу агентов или сервер без необходимости.
Ветки `task/TASK-XXX-short-name`, коммиты `TASK-XXX: результат`, PR по шаблону.
Не force-push, не удалять историю, не пушить секреты/ключ подписи, не открывать приватный проект публике без указания.
Слияние — после проверок и ревью, с соблюдением настроек репозитория. Магазины приложений — отдельное разрешение.
Не считать CI запущенным, если workflow только добавлен; не считать APK собранным без реального файла и лога.
Фиксировать версии инструментов. Не подставлять latest и не выдумывать работающие команды сборки.

## 7. Остановка, передача и возобновление
Перед лимитом контекста/концом сессии создать handoff по шаблону; указать реальные пути, HEAD, проверки, остаток, следующий шаг.
При внезапном обрыве следующий агент сверяет Git и файлы, не повторяет действия с денежными операциями/публикацией вслепую.
Если инструмента/сети нет: BLOCKED только соответствующая задача, точная причина и безопасное продолжение.
Не обещать фоновую или будущую работу без реально работающего планировщика.

## 8. Уточнение gates и неизменяемых снимков
Дополнительно читать state/DECISIONS.json. Решение открывает gate только при ACCEPTED с источником ответа Артура.
Approval gate = максимальная версия ID; старое APPROVED не разрешает новую NEEDS_REAPPROVAL.
Материалы утверждений хранить неизменяемыми снимками approvals/materials/ID/vN/.
DONE хранит исторические версии; активная задача и новый выпуск требуют актуального утверждения.
Исполнитель не пишет реестр, а передаёт запись координатору; координатор не придумывает ответ владельца.
