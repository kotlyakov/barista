# Оркестрация и передача работы

## Роли и ответственность
| Роль | Делает | Не делает |
|---|---|---|
| Координатор | Выбирает готовую задачу, следит за зависимостями, интегрирует и обновляет общее состояние | Не утверждает за Артура |
| Геймдизайнер | Правила, рецепты, экономика, калибровка; предложения с аргументами | Не меняет исходные требования |
| Техлид | Стек, границы модулей, контракты, сборка | Не строит лишнюю инфраструктуру |
| Разработчик | Код назначенной задачи и содержательные проверки | Не редактирует чужую область |
| Художник/UI | Варианты, макеты, ресурсы и демонстрации анимаций | Не делает свой выбор финальным |
| Звук | Набор прослушивания, источники и лицензии | Не встраивает неутверждённое как финал |
| QA/ревьюер | Сверяет требования, проверяет ошибки и регрессии | Не ставит APPROVED визуалу/звуку |
| Интегратор/релиз | Собирает ветки, APK и доказательства | Не публикует в магазин без указания |

## Выбор следующей работы
1. Сверить активные задачи, зависшие аренды и незавершённые ветки.
2. Сначала исправления блокирующих дефектов, затем наименьший приоритетный TASK с deps=DONE и нужными approvals=APPROVED.
3. TODO без выполненных зависимостей не исполнять. Отсутствие доступа к GitHub не блокирует всю документацию.
4. Дать исполнителю TASK-ID, входной commit, входы, allowed_paths, запреты, критерии, reviewer и форму handoff.
5. Перед интеграцией повторить проверки на итоговой ветке, разрешить конфликты вручную по требованиям.
6. Записать итог: результат, тесты, commit/PR, следующий TASK и блокировки.

## Защита от гонок
Координатор — единственный писатель TASKS.json, PROJECT_STATE, DECISIONS, APPROVALS registry.
Рабочая аренда 4 часа как стартовое правило; lease_until — ISO8601 с зоной. Это не автоматический таймер.
Истекла аренда → inspect branch/worktree/handoff → связаться при возможности → явно назначить заново.
Нельзя иметь двух IN_PROGRESS одной задачи. При малом пуле агентов роли совмещаются последовательно.
Ревьюер не должен быть автором результата; если невозможно, SELF_REVIEW с ограничением и финальное ревью позже.

## Пакет передачи
TASK-ID; base/head commit; изменённые файлы; выполненные критерии; команды и фактические результаты;
непроверенное; дефекты; необходимые утверждения; следующий конкретный шаг. Образец templates/HANDOFF.md.
Для большого контекста сначала короткое state/HANDOFF.md, подробности в handoffs/TASK-XXX-session.md.
Чат между агентами не является долговременным контрактом: значимое решение записать в репозиторий.

## Когда беспокоить владельца
Нужна продуктовая развилка, утверждение макета/звука, невосстановимая потеря/доступ или препятствие без безопасного обхода.
Запрос содержит конкретный материал, версию, варианты и рекомендацию. Один пакет вопросов вместо цепочки мелких уточнений.
Пока ждём, выполнять независимые доступные задачи. Если их нет, честно остановиться с зафиксированным состоянием.

## Уточнения выбора и границ
При выборе задачи проверять также decision_gates по state/DECISIONS.json: нужны ACCEPTED и источник решения Артура.
Перед стартом фиксировать актуальные approval_versions и decision_records. Координатор разрешает только текущую версию утверждения.
Если allowed_paths недостаточны для интеграции, исполнитель перечисляет нужные дополнительные пути и причину;
координатор проверяет конфликты владения и расширяет задачу ДО изменений. При пересечении выполняет последовательно.
TASK-001 завершается за проверку и предъявление ТЗ. Ответ владельца может прийти позже;
до SPEC-001 APPROVED программирование блокировано, но подготовка вариантов графики/звука доступна.
Геймдизайнер готовит D03 до TASK-014, разработчик реализует; запрос D02/D03 готовится заранее, без ожидания соответствующего этапа.
Подготовленная задача на утверждение не означает наличие согласия: интеграция ждёт своего gate.
