# Утверждение ТЗ, макетов, графики и звука
Статусы: DRAFT → PRESENTED → APPROVED / CHANGES_REQUESTED / REJECTED.
Изменение одобренного файла → NEEDS_REAPPROVAL новой версии. Старый APPROVED остаётся историей.

## Что предъявлять Артуру
- ТЗ: версия документа и список открытых продуктовых решений.
- Стиль: 2–3 сравнимых варианта стойки с одним рецептом и героем.
- Макет: полный игровой экран в целевой ориентации, подписи зон, состояния полос, выдача и деньги.
- Прочие экраны: магазин, итог смены, настройки, обучение; реальные размеры текста и зоны safe area.
- Анимации: короткое видео/GIF с длительностью и триггерами, включая перетап и неуспешный drop.
- Герои: лист с именами, силуэтами, выражениями и одним игровым примером.
- Звук: воспроизводимый набор WAV/OGG или прослушивание, таблица «событие → файл», отдельные музыка/эффекты.
У звука нужна возможность прослушать сам звук. Описание словами не является звуковым утверждением.

## Обязательная запись в REGISTRY.json
id, category, version, status, artifact_paths, sha256, presented_at, approved_by,
source_message, scope, supersedes. Для нового черновика неизвестные поля null/пустые.
APPROVED допустим только с именем Артур, ссылкой или точным текстом его сообщения,
непустым списком файлов и SHA256 каждого файла. Координатор записывает решение; другие агенты его не придумывают.
Хеш фиксирует конкретные байты, а не правдивость цитаты; QA сверяет с реальным сообщением владельца.
Если утверждён пакет, scope перечисляет содержимое; не распространять одобрение одного героя на всех.

## Интеграция
Технические заглушки разрешены до финальной графики, без имитации утверждения.
Финальная сборка использует только утверждённые версии ресурсов с подходящей лицензией.
Проверять соответствие размеров/цветов/анимаций реализации одобренному макету отдельно.
При правках опубликовать сравнение до/после, не заменять старые материалы без следа.

## Текущая версия и исторические результаты
Gate разрешается по записи максимальной version для данного id, а не по любому старому APPROVED.
Для активной интеграции/релиза текущая версия должна быть APPROVED и хеши должны совпадать.
Перед предъявлением скопировать материалы в неизменяемый каталог approvals/materials/ID/vN/;
artifact_paths и хеши ссылаются на эти снимки. Рабочий GAME_SPEC/макет может развиваться отдельно.
При новой версии не менять байты старого утверждённого снимка.
Завершённая задача хранит approval_versions: {ID: N}; её историческое DONE не исчезает при новых правках.
Новая версия создаёт задачу на обновление/проверку соответствия. В выпуск допускается только актуальная версия.
Исполнитель готовит шаблон запроса/результата; координатор единолично вносит запись REGISTRY.
Задачи подготовки 003/010/015/017 могут быть DONE после предъявления и фиксации статуса PRESENTED;
ожидание одобрения выражается в gate интеграционной задачи, а не в ложном APPROVED.
